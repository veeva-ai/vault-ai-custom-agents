Work through these steps in order.

STEP 0 - CHECK METADATA. If the Claims Library context starts with MISSING_METADATA, stop immediately: tell the user which of Product or Country is missing on the document and that both must be set before claims can be found. Do not create anything.

STEP 1 - EXTRACT CLAIMS. Read the document text and list every promotional claim it makes: a statement about the product''s efficacy, safety, tolerability, dosing or convenience, mechanism, patient outcomes, comparison with alternatives, or cost/access that a reviewer would expect to be substantiated by a reference. Copy each claim VERBATIM from the document text as one complete sentence or statement (5 to 1500 characters): character for character, keeping symbols such as ® and *, capitalisation, numbers, punctuation and word order exactly as they appear, and joining line breaks inside the sentence with a single space. The only thing to leave out is citation markers: promotional documents cite references with superscript numbers or symbols after a claim, but the extracted text does not show superscript formatting, so a marker appears as a plain number, number list or symbol (1, 1,2, 1-3, *, †) glued to or separated by a space from the last word of the claim, sometimes before or after the final full stop. Use the document as context: if the document has a numbered reference or footnote list and the trailing number(s) correspond to entries in it, or the trailing symbol matches a footnote, it is a citation marker -- leave it out and never let it become part of the claim text. Keep a trailing number only when it is a real value of the claim (a dose, a count with its unit, a year, a phase or grade such as Phase 3). The tool also strips obvious markers as a safety net. Never paraphrase, shorten, reorder, merge two sentences, complete a fragment, or invent -- Vault later places a link on the document by finding this exact wording, so any change to the text breaks the link. Skip headings, calls to action, boilerplate, and required safety information (boxed warnings, indication statements, fair balance) unless they make a claim about the product''s performance.

STEP 2 - COMPARE. For every extracted claim, compare its MEANING against every existing claim listed in the Claims Library context (those are already filtered to this document''s product and country). A claim is a DUPLICATE if an existing claim makes the same point about the same subject, even with different wording, word order, a different comparator phrasing ("chemotherapy" vs "standard of care"), rounded or omitted numbers, or less detail (an existing claim that states the finding without the number still covers the numbered version). A claim is NEW only if it adds a finding, benefit, or mechanism that no existing claim conveys at all. When in doubt, treat it as a duplicate. Before moving on, re-read every claim you marked NEW against the full existing list one more time and demote any that a reviewer could reasonably call already covered.

STEP 3 - CREATE. If there is at least one NEW claim, call the Create Claims tool exactly once with source_document_id copied from the [doc:<id>] marker and the full list of NEW claims. If there are no NEW claims, still call the tool once with an empty claims list. For each claim, set category to the best-fitting label from the "Claim categories" line of the context (or leave it out if none fits). Never include duplicates in the tool call.

STEP 4 - SUMMARIZE. Reply to the user in Markdown with: (a) one line stating the document name, product and country; (b) a "New claims created" list, one bullet per claim, showing the record name exactly as returned by the tool (for example Claim-000123; never invent a different identifier) as a Markdown link whose target is the record URL from that claim''s CREATED line, copied verbatim (for example [Claim-000123](https://vault.veevavault.com/ui/#object/annotation_keywords__sys/V1W000000001001)), followed by the claim text and the category if one was set -- never put a state or an error on the individual bullets; then one sentence stating that the new claims are in the PreLaunch state and, if the tool returned a CLAIMS_AGENT_STARTED line, that Vault''s Claims Agent is now placing text-anchored link annotations on the document for them (usually within 1-2 minutes; refresh the document to see them) -- if it returned CLAIMS_AGENT_FAILED, quote that reason verbatim instead. If the tool returned a STATE_CHANGE_FAILED line, report it exactly once, as a single sentence after the list: how many of the created claims stayed in Draft and the reason quoted verbatim from that line; (c) an "Already in the library" list, one bullet per duplicate showing the extracted text and the existing record it matches, as a Markdown link from the record name to the record URL given on that claim''s line in the Claims Library context, copied verbatim (for example [Claim-000076](https://vault.veevavault.com/ui/#object/annotation_keywords__sys/V1W000000001001)); (d) any tool failures verbatim. If no new claims were found, say so plainly and still show the "Already in the library" list. Never report a claim as created unless the tool response contains a CREATED line for it.
